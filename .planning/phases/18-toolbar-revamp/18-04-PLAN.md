<objective>
Add the ONE new piece of plumbing this phase requires: a **reactive** readable Arc on-state seam. Arc mode (`arcMode: 'off'|'sticky'`) lives in `useMarkupTool` React state and is exposed only as *setters* through `markup-arc-ref.ts` — there is no getter, so a rail/context Arc toggle can fire but cannot show whether Arc is on (Pitfall 1, R-2).

A plain module-variable getter (mirroring `getChainArmedItem`) is NOT enough here. `getChainArmedItem` stays visually current only because arming a chain *coincides with* a `setActiveTool()` store change that re-renders sibling components (see `CanvasViewport.tsx:130-186` and the coincident `setActiveTool` at ~:1120-1130). Arc has no such coincident store change: **`Shift+A` flips `useMarkupTool` local state only** (`useKeyboardShortcuts.ts:~187-300`), so a bare module-var read would leave `ToolRail`/`ContextBar` showing stale Arc chrome until an unrelated re-render. The seam must therefore carry its own subscribe/notify.

Mirror the existing setter-ref pattern, then make it observable: add `setArcStickyState(bool)`, `getArcSticky()`, AND `subscribeArcSticky(cb)` (a `useSyncExternalStore`-shaped pair). `CanvasViewport` publishes `arcMode` on every change; `setArcStickyState` notifies subscribers so `ToolRail` (18-07) and `ContextBar` (18-08) re-render on ANY arc change including `Shift+A`.

Purpose: unblocks the Arc on-state chrome on the ToolRail (18-07) and ContextBar (18-08) — SC-2 "Snap/Arc on/off states always visible" — for keyboard-driven arc toggles too.
Output: one new getter + a subscribe/notify pair + a one-line publish effect. No behavior change to arc drawing, no store coupling (arc flags stay OUT of any store — honoring the locked Phase-14 decision "arc flags are NOT in a store", STATE.md:183).
</objective>
